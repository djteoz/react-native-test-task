# Ревью: OptimizationList (Задание №2)

Компонент: `pages/review-list/review-list.tsx`
Документация проекта: `docs/recommendations.md`

## Резюме

Компонент подходит для демо на 9 элементах, но в текущем виде не готов к сценарию со 100+ элементами. Основные проблемы находятся не в бизнес-логике, а в выборе контейнера списка, стабильности данных и структуре компонента.

Главный риск: каждое изменение `value` в `TextInput` пересобирает массив `data`, меняет ключ первого элемента и заставляет список проходить через лишнюю работу. На маленьком массиве это почти не видно, но на мобильном устройстве с большим списком это быстро превращается в просадки FPS, лишние layout passes и повышенное потребление памяти.

**Вердикт:** перед production-использованием компонент стоит рефакторить. Минимальный обязательный шаг — заменить `ScrollView + map` на `FlatList` со стабильными ключами.

## Findings

### High: `ScrollView` не подходит для большого динамического списка

Сейчас список рендерится через `ScrollView` и `data.map(...)`. `ScrollView` монтирует все дочерние элементы сразу, поэтому при 100+ строках приложение будет выполнять работу для всего списка, включая элементы вне экрана.

Для React Native best practice — использовать виртуализированный список:

- `FlatList` из коробки React Native;
- `SectionList`, если список нужно группировать;
- `FlashList`, если в проекте допустима внешняя зависимость и нужны дополнительные perf-оптимизации.

Рекомендуемый вариант для этого компонента — `FlatList`.

### High: нестабильный `key={item.title}`

`title` не должен использоваться как ключ:

- первый элемент равен `value`, значит key меняется при каждом символе;
- пустой `value` даёт пустой ключ;
- в реальных данных `title` может повторяться.

Из-за этого React может размонтировать и заново монтировать строки вместо обновления существующих. Для списка нужен стабильный `id`, а в `FlatList` — `keyExtractor`.

### High: динамический первый элемент пересобирает список при каждом вводе

Первый элемент массива зависит от `value`:

```tsx
const data: TData[] = [
  {title: value},
  {title: '1'},
  ...
];
```

Каждый ввод символа создаёт новый массив и новый объект первого элемента. При большом списке это не лучший путь: состояние input связано со всем массивом, хотя фактически меняется только один визуальный блок.

Если этот элемент гарантированно первый, лучше вынести его из `data` в `ListHeaderComponent`. Если гарантированно последний — в `ListFooterComponent`. Тогда основной массив остаётся стабильным, а изменение `value` затрагивает только header/footer.

### Medium: inline styles создаются на каждый render

В компоненте несколько inline-style объектов: для `TextInput`, row-контейнера и индикатора. Это ухудшает читаемость и создаёт новые ссылки на стили при каждом render.

По `docs/recommendations.md` стили должны быть вынесены в отдельный файл `{name}.style.ts`. Для этого компонента ожидаемый файл — `review-list.style.ts`.

### Medium: row лучше вынести в отдельный memoized-компонент

Сейчас row описан прямо внутри `map`. После перехода на `FlatList` строку лучше вынести отдельно:

- `ReviewListItem`;
- `React.memo(ReviewListItem)`;
- `renderItem` завернуть в `useCallback`, если он зависит от внешних значений;
- статический массив данных вынести из компонента или мемоизировать.

Это снижает вероятность лишних перерисовок строк при изменении `value`.

### Medium: структура не соответствует рекомендациям проекта

`docs/recommendations.md` описывает формат:

- `{name}.model.ts` — интерфейсы;
- `{name}.style.ts` — стили;
- `{name}.tsx` — компонент.

Сейчас тип `TData` и все стили находятся внутри `review-list.tsx`. Для мини-задачи это допустимо, но для поддерживаемого компонента лучше привести структуру к проектному соглашению.

### Low: порядок данных выглядит подозрительно

В тестовом массиве `'6'` стоит перед `'5'`. Возможно, это просто демо-данные, но если порядок важен, стоит проверить источник данных или явно отсортировать список до передачи в компонент.

## Ответ на доп. вопрос

> Если элемент всегда первый или последний — можно оптимизировать?

Да. Это как раз хороший случай для `ListHeaderComponent` или `ListFooterComponent`.

Если элемент всегда первый:

```tsx
<FlatList
  data={items}
  ListHeaderComponent={<DynamicItem title={value} />}
  renderItem={renderItem}
  keyExtractor={keyExtractor}
/>
```

Если элемент всегда последний:

```tsx
<FlatList
  data={items}
  ListFooterComponent={<DynamicItem title={value} />}
  renderItem={renderItem}
  keyExtractor={keyExtractor}
/>
```

Плюс этого подхода: `items` не зависит от `value`, значит при вводе текста не нужно пересоздавать весь массив и не нужно заново прогонять reconciliation по статическим строкам.

## Рекомендуемый рефакторинг

1. Заменить `ScrollView` на `FlatList`.
2. Вынести `TextInput` в `ListHeaderComponent`.
3. Если динамическая строка всегда первая — тоже разместить её в header рядом с input. Если последняя — в footer.
4. Добавить стабильный `id` в модель элемента.
5. Использовать `keyExtractor={(item) => item.id}` вместо `key={item.title}`.
6. Вынести row в `ReviewListItem` и обернуть в `React.memo`.
7. Вынести стили в `review-list.style.ts`.
8. Вынести типы в `review-list.model.ts`.
9. Для строк фиксированной высоты добавить `getItemLayout`, если это реально соответствует дизайну.

Пример целевой структуры:

```text
pages/review-list/
  review-list.tsx
  review-list.model.ts
  review-list.style.ts
```

## Итог

Основной комментарий по компоненту: текущая реализация не масштабируется как мобильный список. Для 9 элементов она работает, но для 100+ нужно перейти на виртуализацию, стабильные ключи и изоляцию динамического элемента от основного массива данных.

Самая важная оптимизация по доп. вопросу: если `value`-элемент всегда первый или последний, не хранить его в общем `data`, а вынести в `ListHeaderComponent` или `ListFooterComponent`.
